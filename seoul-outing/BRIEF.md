# 서울 나들이 코스 앱 — 프로젝트 브리프

캐스팅(50인 에이전트 팀) 투입 전 사전 정리 문서. 로컬 세션에서 `/casting` 실행 시 이 파일을 입력으로 쓴다.

## 1. 무엇을 만드는가

주말에 서울 및 서울 근교로 나가는 **반나절 나들이 코스**를 짜주는 앱.

- 기준 일정: **오전 10시 출발 ~ 저녁 무렵 귀가** (약 8~10시간)
- 사용자가 첫 화면에서 몇 가지 조건(크라이테리아)을 고르면
- 추천 코스와 **시간표**를 뽑아준다

## 2. 화면 흐름

```
1단계  "오늘의 나들이 컨셉은?"
       산책 / 공연 / 전시 / 쇼핑 / 유적지 관광 / 뒷골목 탐색 / 사진찍기 …

2단계  "오늘 땡기는 음식은?"
       음식 카테고리 선택

3단계  출발지 입력
       → 목적지까지 대중교통 기준 최적 루트 제시

4단계  하루 나들이 코스 + 시간표 출력
```

## 3. 하드 제약 (리포 컨벤션 — 협상 대상 아님)

이 저장소의 모든 앱이 지키는 규칙이다. 새 앱도 따라야 한다.

| 제약 | 내용 |
|---|---|
| **단일 파일** | `index.html` 하나로 끝난다. 빌드 스텝 없음 |
| **서버 없음** | 백엔드 없음, 계정 없음, 로그인 없음 |
| **네트워크 없음** | 리포 전체에 `fetch()` 호출이 **0건**. 인터넷이 끊겨도 동작해야 함 |
| **저장은 localStorage만** | 데이터가 브라우저 밖으로 나가지 않음 |
| **API 키 불가** | 공개 저장소이므로 키를 넣을 수 없음 |

가장 가까운 선례: **`meal-planner/`** (이번 주 식탁).
"조건을 고르면 주간 식단표·레시피·장보기 목록을 뽑아줌" — 입력 형태(조건 선택)와
출력 형태(계획표)가 이번 앱과 사실상 같은 구조다.
단일 파일 131KB, 데이터를 `DISHES` / `MEALS` / `GROUPS` 같은 상수로 파일 안에 박아두고
클라이언트에서 조합·스코어링한다. **이번 앱의 기본 참조 아키텍처.**

## 4. 최대 쟁점 — 대중교통 루트

요구사항의 "대중교통 기준 최적 루트"가 위 제약과 **정면으로 충돌한다.**
캐스팅 팀이 가장 먼저 결론 내야 할 항목.

선택지:

- **A. 지하철 그래프 내장** — 수도권 전철 역·환승 정보를 파일 안에 박아두고
  최단 경로를 직접 계산. 오프라인 유지 가능. 버스는 포기하거나 근사치.
- **B. 외부 지도 앱으로 위임** — 코스는 앱이 짜고, 실제 길찾기는
  카카오맵/네이버지도 딥링크로 넘긴다. 제약 위반 없음. 정확도는 지도 앱 수준.
- **C. 실시간 API 호출** — 정확하지만 서버·API 키가 필요해
  **리포 컨벤션을 깬다.** 채택하려면 별도 판단 필요.

현재 기울기: **A + B 조합** (코스 설계는 내장 그래프로 소요시간 추정,
실제 길안내는 지도 앱 위임). 단, 최종 결정은 캐스팅 팀 몫.

## 5. 필요 역량 축 (캐스팅 매칭 기준)

| 축 | 왜 필요한가 |
|---|---|
| **로컬 콘텐츠 / 큐레이션** | 서울·근교 장소 DB. 컨셉별(산책·전시·뒷골목…) 후보지 선정. **이 앱의 진짜 자산** |
| **경로 · 시간 알고리즘** | 이동시간 추정 + 10시~저녁 타임라인 스케줄링 (제약 만족 문제) |
| **지도 연동** | 딥링크 설계, 좌표 데이터 관리 |
| **선택형 온보딩 UX** | 컨셉 → 음식 → 출발지 3단 질문의 이탈률 |
| **F&B 도메인** | 음식 카테고리 분류, 코스 내 식사 타이밍 배치 |
| **프론트엔드 구현** | 타임라인 UI, 단일 파일 내 렌더링 |

## 6. 열린 질문

- 근교의 범위는? (경기도 전역 / 수도권 전철 도달권 / 편도 90분 이내)
- 계절·날씨를 반영하나? (오프라인이면 실시간 날씨는 불가 — 계절만 가능)
- 코스 하나만 주나, 여러 개 중 고르게 하나?
- 장소 데이터 규모는? (meal-planner 수준이면 수백 건)
