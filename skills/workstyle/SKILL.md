# 스틸 워크 스타일 콘텐츠 만들기

곤사마(@POSCO)가 만든 직장인 업무 스타일 자가진단 웹앱. 팀 워크숍·신입 온보딩에서
쓰는 것을 전제로 만들었다. 다른 언어 학습 앱들과 달리 "회차"가 계속 늘어나는 구조가
아니라, **정해진 8축 32문항 위에 결과·궁합 카피를 다듬어 가는 앱**이다.

| | 내용 |
|---|---|
| 대상 | 직장인 — 자기 진단 + 상사·동료·후배와의 궁합 확인 |
| 구조 | 8축 32문항(약 5분), 직책자/팀원 역할 분기, 결과 저장·공유, 1:1 궁합, 팀 지도 |
| 명세 | `references/schema.md` |
| 설계 근거 | `README.md`, `src/문항설계_v2.html` (문항 전문 + 축별 이론 근거, v2에서 뺀 8문항과 그 이유 포함) |

## 절대 어기면 안 되는 세 가지 원칙

이 앱을 만들 때 사용자가 직접 정한 원칙이다. 콘텐츠를 새로 쓸 때마다 다시 확인한다.

**1. 검사가 아니라 대화 도구다.** "당신은 ○○형"이라고 단정하지 않는다. 성격 특성은
연속 분포이지 유형으로 딱 갈리지 않는다는 게 전제다. 새 카피에도 유형 명사(예: "속도형
인간")를 만들어 붙이지 말고, 축마다 기울기로 말한다.

**2. 궁합은 판정이 아니라 처방이다.** "안 맞음"으로 끝내지 않고 "이렇게 하면 통함"으로
쓴다. 닮은 조합(`CB[i].same`)도 "잘 맞음"으로 끝내지 않는다 — 둘이 함께 놓칠 맹점을
반드시 같이 알려준다. 관계(상사·동료·후배)에 따라 조언이 달라져야 한다(`act`, `CLOSING`).

**3. 인사 평가에 쓰지 않는다.** 이 문항은 학술적으로 타당화된 검사가 아니다. 심리학·
조직심리학 이론(`references/schema.md` 상단 표 참고)은 문항과 조언을 만드는 **근거**일
뿐이다. **MBTI는 쓰지 않는다**(재검사 신뢰도가 낮고 이분법적이라 사용자가 명시적으로
배제함). **뇌과학도 쓰지 않는다**(이 영역에서 실증적으로 말해줄 게 거의 없어 유사과학
취급받기 쉽다 — 조직에서 쓰는 도구의 신뢰를 깎는다). 앱 안에 "채용·평가·배치의 근거로
쓰지 말 것"이라는 고지가 있어야 한다.

## 작업 순서

1. **뭘 고치는지 먼저 정한다** — 문항 문구, 에피소드(`EP`), 결과 카피(`P`),
   어울리는 일(`FIT`), 궁합 문구(`CB`) 중 어디인지. `references/schema.md`에서
   정확한 필드를 찾는다. 요청이 "결과가 밋밋하다" 쪽이면 거의 항상 `EP`다.
2. **근거를 확인한다** — 새 이론적 근거를 대야 한다면 `src/문항설계_v2.html`의 방식대로
   실제 연구(Big Five, 오하이오 리더십 2요인, 해석수준이론, 조절초점이론, 공손성 이론,
   자기결정이론, 스트레스 대처 이론 등)를 찾아 붙인다. 지어낸 이론명을 쓰지 않는다.
3. **톤을 맞춘다** — 존댓말, 담백하게. 약점(`wk`)은 "못 한다"가 아니라 "기본값과
   반대라 노력이 더 든다"로 쓰고, 구체적 실천 하나로 문단을 닫는다.
4. **역할 대칭을 확인한다** — 문항에 `alt`(팀원용)를 추가하거나 고칠 때, **축과 a/b가
   가리키는 극이 leader/member 양쪽에서 완전히 같아야 한다.** 장면만 바뀌지 채점
   방향은 안 바뀐다. 이게 깨지면 두 사람의 결과를 코드로 비교할 수 없게 된다.
5. **개수 규칙을 지킨다** — 축마다 문항 4개, `EP[i]`는 L/R 두 극 전부,
   `FIT[i].tips`는 항상 3개, `CB[i].act`는 L/R 두 극 각각 상사·동료·후배 세 관계 전부.
6. **전달** — 고친 필드만 잘라 `.js` 파일로 정리해 보내거나, 사용자가 요청하면 아티팩트를
   직접 고친다(아래 "앱에 넣기" 참고).

## 표기·문체 규칙

- 한국어 문자열 안에서 인용할 때는 `"..."` 대신 「」를 쓴다.
- 강조는 `<b>...</b>`. 에피소드(`EP`, `CB[i].ep`) 안에서만 대사에 `<q>...</q>`,
  속으로 하는 말에 `<i>...</i>`를 추가로 쓴다. 그 외 태그는 쓰지 않는다.
- 문장은 짧게, 두세 문장 단위로 끊는다. 이모지는 쓰지 않는다.
  느낌표는 **에피소드 속 대사 안에서만** 허용한다(사람이 실제로 그렇게 말하기 때문이다).
- 유형을 단정하는 말("당신은 ○○형입니다") 대신 "○○ 쪽으로 기울어 있습니다" 식으로 쓴다.
- **화면은 밝은 한 벌뿐이다.** 다크 모드는 사용자가 보고 "필요 없다"고 걷어냈다.
  `prefers-color-scheme` 분기나 `[data-theme]` 팔레트를 다시 넣지 않는다.
  `:root`에 `color-scheme:light`가 있어야 기기가 다크여도 화면이 뒤집히지 않는다.

## 앱에 넣기

데이터가 앱 파일 안에 박혀 있다(붙여넣기 화면이 없다). 언어 학습 앱들과 달리 폰트를
심지 않아 파일이 작다(약 140KB).

**A. 저장소를 직접 고치기 (기본값)** — 앱은 `my-web-apps` 저장소의 `workstyle/`에 있다.

| 파일 | 내용 |
|---|---|
| `workstyle/index.html` | 앱 본체. 모든 데이터 상수가 여기 있다 |
| `workstyle/manifest.json`, `sw.js`, `icon*` | 설치·오프라인용. 콘텐츠만 고칠 때는 건드리지 않는다 |
| `workstyle/src/문항설계_v2.html` | 설계 문서. 문항을 고쳤으면 여기도 같이 고친다 |

`sw.js`의 `VER` 문자열은 **앱 파일을 고쳤을 때만** 올린다. 안 올리면 이미 설치한
사람에게 옛 화면이 계속 나온다.

**B. 고친 부분만 전달** — 사용자가 파일로 받길 원하면 고친 필드(`Q[i]`, `EP[axis][side]`,
`P[axis][side]`, `FIT[axis][side]`, `CB[axis]` 등)를 코드 조각으로 정리해 보낸다.

어느 쪽이든 **고치고 나면 브라우저로 실제로 열어 한 판 끝까지 풀어본다.** 문항 수를
바꿨다면 결과 코드가 양 끝(`AAAA-AAAA` / `WWWW-WWWW`)까지 나오는지 확인한다 —
환산이 깨지면 여기서 먼저 티가 난다.

## 사용자에 대해

사용자는 본인을 "컴맹"이라고 말한다. 기술 용어를 앞세우지 말고, 무엇을 왜 하는지 짧은
문장으로 설명하고, 파일을 어디에 어떻게 넣는지는 단계별로 안내한다. 결과물은 항상
파일로 만들어 보낸다.
