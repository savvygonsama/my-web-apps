# 스틸 워크 스타일 — 데이터 구조

`index.html` 안의 `<script>`에 상수로 박혀 있다. 앱을 고치려면 아래 이름을 그대로 찾는다.

## AXES — 8축 정의

```js
const AXES = [
 {n:"추진 템포",     L:"속도형",        R:"완성도형"},
 {n:"우선순위",      L:"과업 중심",     R:"관계 중심"},
 {n:"의사결정",      L:"주도형",        R:"조율형"},
 {n:"시야",          L:"큰그림형",      R:"디테일형"},
 {n:"변화 대응",     L:"검증 후 이동",  R:"일단 시도"},
 {n:"피드백 방식",   L:"직설형",        R:"완곡형"},
 {n:"일 맡기고 받기",L:"자율 선호",     R:"절차 선호"},
 {n:"압박 상황",     L:"정면 돌파",     R:"거리 두고 재정비"}
];
```

인덱스 순서(0~7)가 `Q[i].x`, `P[axis]`, `FIT[axis]`에서 그대로 축 번호로 쓰인다.
**축을 추가·순서 변경하면 코드 자릿수(`SW-□-XXXX-XXXX`)와 채점이 전부 어긋난다.** 하지 않는다.

## Q — 32문항 (축마다 4개)

```js
{x:0, s:"상황 문장", a:"L쪽 답", b:"R쪽 답",
 alt:{s:"팀원용 대체 상황", a:"팀원용 L쪽 답"} }   // alt는 역할 분기가 필요한 문항에만
```

- `x`: 이 문항이 속한 축(0~7). 축마다 정확히 4문항.
- `s/a/b`: 직책자(leader) 화면 기본값.
- `alt`: 팀원(member)에게는 성립하지 않는 상황(예: "팀원이 실수했다", "일을 맡길 때")을
  갈아끼우기 위한 것. `alt` 안에 없는 키는 기본값을 그대로 쓴다(`txt()` 함수 참고).
  **alt를 추가해도 그 문항이 속한 축과 a/b가 어느 극을 가리키는지는 절대 안 바뀐다** —
  장면만 바뀌지 채점 방향은 leader/member 동일해야 두 결과를 비교할 수 있다.

## EP — 축별 에피소드 (결과 화면의 첫 섹션)

`EP[axis]`는 배열 2개: `[L극 장면, R극 장면]`. 균형일 때는 `EPBAL` 하나를 공통으로 쓴다.

```js
{t:"「대사」 같은 장면 제목",
 sc:"장면 — 대사가 있는 사무실 상황. 직책자 화면 기본값",
 s2:"팀원 자리에서 본 같은 장면 — 필요한 축에만. 없으면 sc를 그대로 쓴다",
 heart:"<b>상대 속마음</b> — 그 자리에 있던 사람이 속으로 한 말",
 fix:"그래서 이렇게 — 다음 주 월요일에 바로 할 수 있는 것 하나"}
```

이 앱에서 사람들이 **가장 먼저, 그리고 거의 유일하게 끝까지 읽는 부분**이다. 규칙이 있다.

- `sc`는 **설명이 아니라 장면**이다. 요일·시각·대사가 들어간다. 대사는 `<q>...</q>`로
  감싸면 화면에서 말풍선처럼 강조된다. 속으로 하는 말은 `<i>...</i>`.
- 주인공을 **나쁜 사람으로 그리지 않는다.** "옳은 질문입니다. 완벽하게 옳습니다."처럼
  그 행동이 왜 합리적인지를 먼저 인정하고, 그런데 상대에게는 어떻게 닿았는지를 보여준다.
- `heart`는 **판단이 아니라 사정**이다. 상대를 피해자로 만들지 않는다.
- `fix`는 **하나만**, 그리고 반드시 실행 가능한 크기로. "여섯 글자만 붙이세요"처럼
  당장 할 수 있는 것이어야 한다. 성격을 바꾸라는 조언은 쓰지 않는다.
- `s2`는 그 장면이 **직책 권한을 전제할 때만** 쓴다(예: "팀원이 실수해서 왔다").
  권한과 무관한 장면은 `sc` 하나로 양쪽 자리에 다 통한다.

## P — 축별 강점·약점 프로필

`P[axis]`는 배열 3개: `[L극 프로필, R극 프로필, 균형(중간) 프로필]`.

```js
{adj:"빠르게 움직이는", sum:"빠르게 움직이는",
 st:{t:"강점 한 줄 제목", d:"강점 설명 2~3문장"},
 wk:{t:"약점 한 줄 제목", d:"약점 설명 + 실천 팁 1개(문장 안에 녹여 씀)",
     d2:"관계(down·후배)일 때 쓰는 대체 문구 — 선택"},
 mir:"이 사람과 일하는 상대方 눈에는 어떻게 보이는지, '다만' 뒤에 아쉬운 점 한 줄"}
```

균형 프로필(세 번째 항목)은 `st`/`wk` 없이 `{sum, mir}`만 있다 — 강점·약점을 가르지 않는다.

**약점(`wk`) 톤 규칙**: "못 한다"가 아니라 "기본값과 반대라 노력이 더 든다"로 쓴다.
`d`는 비난이 아니라 구체적 실천 하나로 끝난다.

## FIT — 축별 어울리는 일 / 힘이 더 드는 일

`FIT[axis]`도 배열 2개: `[L극, R극]`. 균형(중간)에는 FIT가 없다 — 결과 화면에서
±2 이내는 `BAL` 문구로 대체한다(아래).

```js
{g:"어울리는 일 — 예시들",     // "성패를 가르는 일" 형태로 구체적 업무 나열
 h:"힘이 더 드는 일 — 예시들",  // 못 한다가 아니라 더 애써야 하는 영역
 tips:["실천 팁 1", "실천 팁 2", "실천 팁 3"]}   // 정확히 3개
```

- `g`/`h`는 부서·직무 예시를 구체적으로 든다(예: "긴급 클레임 대응, 신규 문의 초동").
  추상적으로 쓰면("빠른 일이 어울림") 자기 얘기로 안 읽힌다.
- `tips`는 **항상 3개**, 하나는 "왜 그런지"까지 붙인 한두 문장.
- 배치·평가 근거로 오해되지 않게, 앱 어딘가에 이 문구가 조언이지 판정이 아니라는 안내가
  있어야 한다(현재 결과 화면 상단 고지 참고).

## BAL — 균형(중간) 결과 공통 문구

```js
const BAL = {t:"이 축은 한쪽으로 기울지 않았습니다",
 d:"상황에 따라 다르게 움직인다는 뜻이고, 그 자체는 약점이 아닙니다. ..."};
```

축 이름과 무관하게 공용으로 쓰는 문구 하나뿐이다. 축별로 다르게 쓰고 싶어지면,
그건 사실 그 축의 L/R 프로필(`P`)을 손볼 자리라는 뜻이다 — `BAL`을 늘리지 않는다.

## CB — 궁합(코드 비교) 콘텐츠

`CB[axis]`는 객체 하나:

```js
{clash: "이 축에서 반대일 때 생기는 마찰 — 왜 서로 그렇게 보이는지",
 ep:    {t0:"장면 제목",
         sc:"두 사람이 같은 일을 두고 어긋나는 장면",
         me:["내가 L극일 때 읽을 한 줄", "내가 R극일 때 읽을 한 줄"]},
 same:  ["둘 다 L극일 때 함께 놓치는 것", "둘 다 R극일 때 함께 놓치는 것"],
 act:   { L: {up:"...", peer:"...", down:"..."},   // 내가 L극일 때, 상대가 상사/동료/후배
          R: {up:"...", peer:"...", down:"..."} }  // 내가 R극일 때
}
```

- `clash`는 **판정이 아니라 왜 부딪히는지의 메커니즘**을 설명한다("안 맞음"이라고 쓰지 않는다).
- `ep.me`의 두 줄은 **양쪽 다 옳게** 쓴다. 화면에서 나란히 놓이므로 한쪽이 이기면
  그 순간 이 앱은 상대를 탓하는 도구가 된다("당신은 팀을 멈추지 않게 했습니다 /
  당신은 정확한 답을 가져왔습니다"처럼 각자의 기여를 적는다).
- `same`은 닮은 조합도 절대 "잘 맞음"으로 끝내지 않는다 — 둘이 함께 놓치는 맹점을 반드시 짚는다.
- `act`는 관계(상사·동료·후배)에 따라 조언이 달라진다. `CLOSING`이 그 관계별 총평을 닫는다.

## CLOSING / RELNAME / ROLE

```js
const CLOSING = {up:"...", peer:"...", down:"..."};  // 관계별 마무리 총평
const RELNAME = {up:"상사", peer:"동료", down:"후배"};
const ROLE = {leader:"직책자", member:"팀원"};
```

## 결과 코드

```
SW-L-AAAW-AAAA
   │ └──┬───┘
   │    └── 여덟 축 점수(-10~+10)를 21단계 문자로. 알파벳 I·O는 헷갈려서 제외.
   └─────── 자리: L=직책자, T=팀원
```

```js
const CH = "ABCDEFGHJKLMNPQRSTUVW";  // 21단계, 인덱스 0~20이 -10~+10에 대응
```

채점은 `show()`가 원점수만 내고 `paint(sc)`가 화면을 그린다. 저장해 둔 결과를 다시
열 때는 `paint()`만 부른다.

축 점수는 그 축 문항들의 a/b 응답 합(문항 4개면 -8~+8)을 **-10~+10으로 환산**해서 쓴다.

```js
const PER = AXES.map((_, x) => Q.filter(q => q.x === x).length);   // 축별 문항 수
Math.round(v * 10 / (PER[x] * 2))                                  // 환산
```

이 환산 덕분에 **문항 수를 바꿔도 기존에 나간 코드가 그대로 유효하다.** 40문항 시절
코드(`SL-`)도 `decode()`가 받아준다. 축을 늘리거나 순서를 바꾸는 것만이 코드를 깨뜨린다.

## 저장·공유·팀 지도

```js
localStorage["sws.me"]    // 내 결과 최대 10건 [{code, role, sc, at, sum}]
localStorage["sws.team"]  // 팀 명단 [{name, code, role, sc}] — 최대 12명
```

`store` 객체가 읽기·쓰기를 전부 try/catch로 감싼다. 사파리 사생활 보호 모드처럼 저장이
막힌 환경에서도 **진단 자체는 굴러가고 저장만 조용히 실패해야 한다.** 이 방어를 걷어내지 않는다.

팀 지도는 축마다 두 가지를 뽑는다 — 기운 사람이 전부 같은 쪽인 축(`lean`, 함께 못 보는 것)과
양쪽으로 갈라진 축(`split`, 회의가 길어지는 자리). 문구는 `CB[x].same` / `CB[x].clash`를
그대로 재사용하므로, 궁합 문구를 고치면 팀 지도도 같이 바뀐다.
